# KYC RAG Pipeline — Hands-On Practice

> **Domain:** Know Your Customer (KYC) / AML Compliance  
> **Stack:** OpenAI Embeddings + GPT-4o · Pinecone Serverless · PyPDF · Python

---

## What You Build

A complete **Retrieval-Augmented Generation (RAG)** pipeline from scratch:

```
KYC PDF
  │
  ▼
[PyPDF] Read pages
  │
  ▼
[tiktoken] Chunk into overlapping token windows
  │
  ▼
[OpenAI text-embedding-3-small] Embed each chunk → 1536-dim vector
  │
  ▼
[Pinecone] Store vectors + metadata (text, page_num)
  │
  ▼  ← INDEXING DONE

User Question
  │
  ▼
[OpenAI] Embed question (same model!)
  │
  ▼
[Pinecone] Cosine similarity search → Top-K chunks
  │
  ▼
[GPT-4o] Generate grounded answer using retrieved context
  │
  ▼
Answer with citations
```

| Score | Meaning |
|-------|---------|
| ≥ 0.80 | Highly relevant — great retrieval |
| 0.60–0.79 | Relevant — acceptable |
| < 0.60 | Weak match — chunk may not contain the answer |

## Key Concepts to Explain in Interviews

### Why RAG instead of Fine-Tuning?
| | RAG | Fine-Tuning |
|--|-----|-------------|
| **Update cost** | Re-index new docs | Re-train model |
| **Hallucination** | Grounded in retrieved text | Can still hallucinate |
| **Domain** | Any document at query time | Baked into weights |
| **Cost** | Cheap (embedding + retrieval) | Expensive GPU training |
| **Latency** | Slightly higher (retrieval step) | Same as base model |

### Why Overlapping Chunks?
A sentence at the boundary of chunk N is also the start of chunk N+1.
Without overlap, a key sentence could be split → retrieval misses it.

### Why Same Embedding Model at Query Time?
Different models produce different vector spaces. Querying with model B
after indexing with model A is comparing apples to oranges → terrible results.

### Why Store Text in Pinecone Metadata?
Pinecone only stores and searches vectors. The actual text must be stored
alongside (as metadata) so you can pass it to the LLM as context.

### The Tipping-Off Problem in Production KYC RAG
If your RAG system is used by bank staff to answer customer queries,
you must ensure retrieved context about SAR filings is never leaked
to customer-facing interfaces. This is a real compliance risk.


I implement a 4-layer defence. 

First, every chunk is tagged with a sensitivity level at ingest time. 

Second, a role-based metadata filter is applied at query time in Pinecone so restricted chunks are never retrieved at all. 

Third, the LLM system prompt explicitly prohibits discussing SARs with customers. 

Finally, a keyword scanner checks every output before it reaches the customer UI and logs any violations as security events."

More questions

**Q1: "Walk me through your RAG pipeline on Azure."**
"My pipeline had four stages. 

First, documents were chunked using RecursiveCharacterTextSplitter and sent to Azure OpenAI's embedding model (text-embedding-ada-002) to generate 1,536-dimension vectors. 

Second, those vectors were indexed into Azure AI Search (formerly Cognitive Search) with the original text stored in the document fields. 

Third, at query time, the user question was embedded using the same model and a vector search was performed. 

Fourth, the top-K retrieved chunks were injected into an LLM prompt as context, and Azure OpenAI (GPT-4o) generated the final grounded response."


**Q2: "What is Hybrid Retrieval and why did you use it?"**


"Pure vector search is great at finding semantically similar content, but it fails on exact matches — for example, if a user types a specific regulation code like 'CBUAE Circular 2023/15', vector search might miss it because the embedding generalises the meaning. Keyword search (BM25) catches exact term matches but misses paraphrased queries.

So I used hybrid retrieval in Azure AI Search, which runs both searches in parallel and fuses the results using Reciprocal Rank Fusion (RRF). This gave the best of both worlds — semantic understanding AND exact term matching — which significantly improved retrieval recall in our KYC domain where regulation codes and entity names are critical."


**Q3: "What is Reciprocal Rank Fusion (RRF)?"**

"RRF is the algorithm Azure AI Search uses to merge the ranked results from vector search and keyword search into a single ranked list. For each document, it calculates a score:

$$RRF_Score = \frac{1}{k + rank_{vector}} + \frac{1}{k + rank_{keyword}}$$




Where k is a smoothing constant (usually 60). A document that ranks highly in both lists gets a very high combined score. This avoids the problem of simply averaging r



**Q4: "How is Azure AI Search different from Pinecone?"**

"Pinecone is a specialized vector database built purely for high-performance vector search at scale — it's optimized for low-latency similarity searches on massive vector datasets.

Azure AI Search is a full enterprise search service. It does vector search, but it also includes rich features like keyword search (BM25), full-text search, faceting, filtering, geospatial search, and data enrichment using cognitive skills. 


In my project, I chose Azure AI Search because I needed hybrid retrieval (vector + keyword) and metadata filtering, which are built-in features of AI Search but would require extra layers to implement in Pinecone. So for enterprise use cases combining structured metadata and unstructured content, Azure AI Search is often a more complete platform than a pure vector database like Pinecone."
